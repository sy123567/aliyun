## -1. 复赛四提交复盘 → 本轮加固

四个并行架构的复赛实测（两位未知司机：广东 + 江浙沪，偏好可能带方言）：

| 分支 | 得分 | 扣分 | token | 决策时间 |
|---|---|---|---|---|
| preference-compile-loop（=#72，确定性调度+LLM编译偏好） | **54407** | **46000** | 425k | 0.96s |
| llm-primary-decisions（LLM 主导逐步决策） | 47894 | 64500 | 922k | 2.26s |
| closed-loop-compliance（双提案仲裁，LLM 每步参与） | 26183 | 69100 | 615k | 1.81s |
| nl-preference-compile-review（编译-评审重构） | 14567 | 84600 | 594k | 1.68s |

**结论：LLM 介入逐步决策越深，得分越差、扣分越高。** 赢家是「LLM 只做偏好
理解/审计/每日计划，执行全部确定性」的 #72。本轮在 master（#72+#73）上做
8 项加固，全部围绕两个目标：**未知司机不丢规则（扣分↓）**、**不过度保守
（毛利↑）**：

1. **去 D001 偏置（毛利↑↑）**：移植 54d4682——「每月长途>8h≤5单」原是全局常量，
   对没有该偏好的复赛司机全季压制最赚钱的长途单。现改为 preference-driven
   （`DriverRules.longhaul_cap_orders`），并新增镜像字段 `allowed_categories`
   （只拉X）、`haul_min_km`（短单不接）。
2. **方言鲁棒（扣分↓）**：抽取/审计/每日计划/语义确认/决策全部 prompt 注入
   `_DIALECT_HINT`（粤语/吴语高频词对照：唔/咪/勿/覅=不、瞓觉=睡觉、返屋企=回家…）；
   离线兜底关键词表补方言词；夜休 fail-safe 支持中文数字钟点（晚上九点/廿三点）
   和 PM 语境（`_extract_clock_times`）。
3. **语义区域归属（毛利↑+扣分↓）**：静态区域表+子串都解析不了的区域名
   （苏南/浙北/方言叫法）走 LLM 地理归属判定（`_city_in_region_sem`，缓存+
   每步预算 6 次新查询）。旧版未知 allowed_region 会拒掉**所有**货整月闲置——
   毛利归零级失败模式；forbidden_region 同理提高召回。
4. **penalty_cap 经济学（毛利↑）**：偏好的累计扣款上限全程透传（记录/抽取/审计/
   每日计划/决策 prompt）。不封顶的每日约束最优先核对；低上限规则不值得为其
   牺牲大量收入——决策 LLM 现在能看到这层经济学。
5. **每日计划防幻觉（毛利↑）**：计划层产出的"今日禁驶窗"若与任何静态窗不相交
   （即全新约束），需过一次语义确认（fail-safe：模型失败/不确定一律保留）。
   防止幻觉窗口每天白吃黄金时段。
6. **无休司机跨午夜接单（毛利↑）**：完全没有休息类约束的司机此前订单也被卡死在
   当天 24:00——纯毛利泄漏。现与弹性休息司机一样可跨夜完单（`_order_finish_deadline`，
   收敛到仿真上界）；并修复 `_pick_order` 终验把扩展截回午夜的旧 bug。
7. **品类指标精确记账（扣分↓）**：评分器按 cargo_name **精确相等**给配额记账；
   解析出的目标名在数据集中原样存在时只数同名货（模糊记账会虚高进度→月底真欠额罚款），
   数据集没有的（方言/噪声）写法才退回语义匹配（生果→水果）。选单与计数同判定。
8. **宽扫描节流（毛利↑）**：k=600 扫描耗 60 仿真分钟；紧急品类猎单时原地重复宽扫
   一天能烧掉数小时。现同地点 150 分钟内无果不重扫（降为 k=200），挪窝后恢复。
   同时修复 urgent 时同一步连扫两次 600 的浪费。
9. **修复 `month_deadhead` NameError**：master 上任何带"月空驶上限"偏好的司机
   在确定性选单时每步崩溃——复赛若有此类偏好整个司机直接报废。

测试：`demo/tests/test_finals_generalization.py`（19 项）+ 既有 39 项全部通过。

### -1.1 价值层升级（对标榜首数据）

榜首（BJTU）：得分 81259 / 扣分 45900 / token 6.4M / 平均决策 3.84s。
**关键读法：扣分与我们最好成绩（46000）几乎相同**——他们没有在合规上赢，
赢的全部是毛收入（约 127k vs 我们 100k，+27%）。token 6.4M ≈ 3.2M/司机
（上限 500 万/司机），而我们只用了 ~0.21M/司机 = **预算的 4%**。结论：
该把闲置的 token 预算花在「价值侧」（选单/接力/调度），合规继续由确定性层
硬守（那是我们已验证的 46k 下限）。本轮升级：

1. **LLM 每步参与决策**（原每 3 步）：`use_llm = consecutive_waits < 3`。
   合规守卫（`_validate_llm_take_order`/`_safe_*`）不变，LLM 只可能在合规
   候选里选得更聪明，不可能放宽约束。预计 token 升至 ~1-2.5M/司机，仍远低于上限。
2. **接力价值（chain value）进入候选**：`_query_cargo` 的扫描缓存现在记录每条
   货的 `net_per_h` + `seen_at` + 装货城市质心（零额外仿真成本），
   `_cargo_liquidity_stats` 聚合成「近 3 天每城市出发货源数量/均价」。
   每个候选标注 `to_liq`（卸货城市的后续市场）——高净值单卸进死城会困车，
   LLM 现在能看到这层。
3. **活跃市场表替代"地理直觉"**：决策 prompt 注入近期实测的货源聚集城市
   （含坐标），reposition 目标从模型臆测改为实际观测。
4. **候选按 net/h 降序取前 12**（原按距离序取前 8——最好的候选经常根本
   不在列表里）；扫描 k 30→50（约 5 仿真分钟，与原混合成本持平）。
5. **战略性闲置守卫**：候选已全部通过合规检查（含今晚禁驶窗前完单），
   LLM 仍要求 wait≥60 分钟且榜首候选 net/h≥80 时，直接改接该单——
   这是此前 LLM-heavy 分支得分崩塌的已记录失败模式（把好货等没了）。

测试合计 63 项（`test_finals_generalization.py` 24 项）全部通过。
注意 §2 的网关不确定性依然成立：评估本轮改动建议至少 2-3 次跑分取均值。

### -1.2 决策 thinking 模式（默认开启 + 4h 跑时保险）

真实网关（qwen3.7-plus）实测：

- 简单探针：thinking 2.9s→8-9s（3 倍）；**真实决策 prompt：均值 ~22s、p90 ~31s**
  （推理链随上下文变长），reasoning ~800 token/步。
- 整月投影：~1.9h/司机 → 复赛两司机 ≈ 3.9h，几乎贴死**4 小时总跑时硬上限**；
  token ~2.3M/司机（5M 内无压力）。
- 合成数据早期对比（前 7 天）：thinking 版成交 24 单 vs 基线 39 单——thinking
  并不必然多赚，待真实数据验证。

实现（`AGENT_DECISION_THINKING`，默认 **1**＝开）：
- 决策调用 `enable_thinking=true`、`max_tokens 180→2000`（思维链占 completion，
  180 会截断 JSON 答案）。其余调用（编译/审计/每日计划/语义确认）不开。
- **跑时保险**：每司机墙钟预算 `AGENT_THINKING_WALL_BUDGET_SECONDS`（默认 6000s
  ＝100min/司机，两司机 3.3h，留 0.7h 余量）。按仿真进度折算，一旦投影超预算，
  该司机**永久降回快速模式**（2s/步），绝不触碰 4h 硬杀线。
- 关闭方式：环境变量设 0。若实测 thinking 不涨分，直接把默认翻回 0 即可。

## 0. 当前架构：闭环偏好编译（面向未知司机泛化）

复赛是两位未知司机（广东 / 江浙沪），偏好为措辞会变的自然语言；旧架构靠
「按 D001 措辞写死的正则补抽 + 关键词白名单接地」做召回，换个说法就漏规则 →
按天复利扣分。新架构（全部在 `demo/agent/model_decision_service.py`）：

1. **逐条编译（LLM 优先）**：每条偏好**单独**调用一次抽取 LLM（不再把全部偏好拼一起批量抽），
   语义接地校验只对照该条原文，互不串扰；新偏好出现时只编译新条目（省 token、免重复合并）。
2. **审计修复（闭环，取代正则补抽层）**：编译后用一次 LLM「覆盖审计」——
   逐条核对偏好原文的全部约束是否都体现在结构化规则清单里（`_audit_preference_coverage` +
   `_describe_rules_for_audit`），缺失部分以**补丁**形式回填（仍走 `_merge_llm_rules` 的接地校验）。
   旧的 `_supplement_basic_rules` / `_supplement_dated_events` 等正则补抽只在**模型不可用**时作为离线兜底。
   （夜休 fail-safe `_supplement_night_failsafe` 因属灾难性规则的最后保险，仍保留。）
3. **零静默丢弃（residual 通道）**：审计后仍无法用结构化字段表达的偏好（如「下雨天不接生鲜」这类
   条件型约束）进入 `DriverRules.residual_constraints`，连同违约金额逐步注入决策 prompt
   （`_format_rules_for_llm` 的【必须遵守·未结构化偏好】块 + `_compliance_self_audit`），
   由决策 LLM 在线遵守。任何偏好都不会被悄悄丢掉。
4. **语义接地全面替换关键词白名单**：`allowed_regions / forbidden_zones / bounded_area /
   must_visit / haul_max_km / daily_order_limit / home_rule` 的关键词门全部改为
   `_confirm_rule_holds` 语义确认；模型给出明确判定时**双向**生效（关键词没命中但语义确认成立
   → 采纳；关键词命中但语义确认不成立 → 丢弃），模型不可用时退回原关键词启发式。
   坐标类高危字段仍保留「原文必须出现显式坐标」的数据门。
5. **每日合规计划层（见 §3.6）**：在编译/审计之外，每个仿真日再用一次小 LLM 调用
   把偏好原文按当天日历（日期/星期/月度进度）具象化为"今日禁驶窗 + 今日要点"，
   守卫按"静态窗 ∪ 当日计划窗"强制执行——覆盖日历条件式偏好（周末时段不同、
   特定日期事件、月度结转）这类静态 schema 表达不了的情况。
6. **执行层**：确定性调度器继续保证已结构化偏好合规（含当日有效禁驶窗），并按净收益择单。

Token 影响：逐条编译 + 一次审计只发生在偏好首次可见时（每司机一次性数次调用），
相对决策循环（每 3 步一次）占比可忽略；逐条编译同时避免了旧版「出现新偏好时全量重抽」的浪费。

测试：`demo/tests/test_preference_compile_loop.py`（逐条编译 / 审计修复 / residual 注入 /
语义门双向判定 / 离线兜底），连同既有 `test_overnight_rest_window.py`、
`test_longhaul_cap_history.py` 共 17 项全部通过。

## 1. 业务背景与要求（来自仓库所有者）

- 本地数据集只有 **D001** 一位司机，仅用于自测。
- **官方复赛是两位司机**：一位**广东**司机，一位**长三角**司机。
- 复赛的偏好（preferences）是**自然语言表述，且措辞会变化**；拿不到司机数据。
  - 因此 agent 必须**通用 / 语言鲁棒**，绝不能写死"深圳 / 水果 / 建材 / 某月"这类 D001 专属逻辑。
- 重点是 **LLM 维护历史决策**（`query_decision_history` → 喂给 LLM 做上下文）。
- 目标是**最大化净收益** `net = 毛收入 − 里程成本 − 偏好罚款`，**不是单纯降罚分**。
  - 毛收入足够高时，带一点罚分是可以接受的——只要净收益够高即可。

### 评分口径（`demo/calc_monthly_income.py`，仓库所有者提供的版本）
- 夜间停车休息：21:00–次日06:00 不得接单/空驶（周末可晚 2 小时）。
- 四月：水果类满 12 单，少一单扣一次（`penalty_amount`）。
- 五月：建材类满 12 单；**四月水果欠额由"五月水果"补**（`may_fruit_makeup_orders`
  抵 `april_shortfall`），未补足 + 五月建材未达标都按"少一单扣一次"计，且罚更重。
- 月度长途（>8h）≤ 5 单，超一单扣一次（**软上限**：净收益 > 罚金时仍值得接）。

跑分命令：
```bash
# 1) 跑仿真（需要 DASHSCOPE_API_KEY；大数据集先开 swap，见 §5）
cd demo/server && DASHSCOPE_API_KEY=sk-... python main.py
# 2) 评分（产出 demo/results/monthly_income_202603.json）
cd demo && python calc_monthly_income.py
```
模型名用 **`qwen3.7-plus`**（网关里写 "3.7plus" 会 model_not_found）。

## 2. ⚠️ 最关键的发现：单次跑分不可比（LLM 网关不确定性）

同一份代码、不同次运行，**净收益能相差 1 万以上**（毛收入在 ~88k–124k 间剧烈波动）。
实测（D001，满月 3–5 月）：

| 版本 | 采样温度 | 第1次 | 第2次 |
|---|---|---|---|
| 原版 agent（master） | 0.1 | 83.1k | 67.2k |
| 本优化（A+B1） | 0.1 | 79.2k | 58.0k |
| 本优化（A+B1） | 0   | 74.3k | 67.5k |

**结论**：
- 这种波动**baseline 自己也有**（67k–83k），是 **LLM 网关（qwen3.7-plus，疑似 MoE）固有的**，
  即使 `temperature=0` 也不能完全消除——不是 agent 代码能消掉的。
- 所以**用单次跑分去判断"某个改动有没有用"是不可靠的**。要比较必须**多次跑取均值/下限**。
- 复赛是**一次性两位司机**，真正该优化的是**抬高下限、降低波动**，而不是赌单次高分。

> 给接手者：如果你要继续调优，请**固定每个版本至少跑 3–5 次**再比较，否则会被噪声误导。

## 3. 本次关键改动（均在 `demo/agent/model_decision_service.py`）

### A1. 去掉 D001 专属硬编码（通用化）
- `_get_category_target()`：删除写死的 `if month_idx==1: 水果12` / `if month_idx==2: 建材12+进位`
  兜底分支。品类指标**只来源于从自然语言解析出的** `rules.monthly_category_targets`。
- `_track_category_order()`：删除只认 `=="水果"/"=="建材"` 的兜底，改为只按解析到的目标品类统计。
- 影响：对复赛未知司机不再错误地去抢"水果/建材"。D001 的品类指标本来就能被解析出来，行为不变。

### A2. LLM 目标对齐"净收益优先"
- system prompt 从"最大化净收入 / 最小化罚款 / 完成指标"改为**首要净收益**；
  接单提示从"高价、**短途**"改为"**净收益(net_per_h)最高**，长途只要 net_per_h 高也值得接"。
- 长途规则措辞改为**软上限**：超 5 单每单扣 1000，但该单净收益明显 > 1000 仍应接。

### A3. 喂给 LLM 的历史摘要改用"权威数据"
- 背景：评测 harness **只调用 `decide()`，从不回调 `update_decision_result()`**，
  所以 `DecisionHistory` 内部计数器恒为 0——原来摘要里一直显示"总接单 0 / 累计收入 ¥0 /
  最近订单全部 ✗"，**会误导 LLM**。
- 改法：`DecisionHistory.get_summary(current_day, plan)` 增加 `plan` 入参，
  累计/本月接单数、长途 x/上限、品类分布**改从每步重建的权威 `plan` 读取**
  （`plan` 由 `_sync_monthly_counts_from_history()` 用 `query_decision_history` 重建）。
  等待/空驶次数与"最近决策动作序列"仍来自本地滚动窗口（这些在 decide 时记录是可靠的）。

### B1. "欠额结转"对齐评分口径（重要！）
- 评分口径里：**四月水果欠额是用"五月水果"来补**的（`may_fruit_makeup_orders`）。
- 但原 `_get_category_target()` 的结转逻辑是把欠额加到**当月第一个品类（建材）**的目标上
  → agent 拼命多接建材（实测接了 21–23 单，远超 12），**对水果欠额毫无抵扣**，
  结果照吃 7000 的五月结转罚。
- 改法：结转时把上月每个品类的欠额加到**当月同一品类**的目标上
  （`targets[cat] += deficit`）。这样五月会去补**水果**，与评分口径一致。
- 该改动**只会更优或持平**：原逻辑给的结转抵扣credit为 0，新逻辑能真正抵扣。
  实测有一次 `mayMakeup=7` 成功把 7000 的五月结转罚降为 0。

### （附）主决策 `temperature: 0.1 → 0`
- 为可复现性改成贪心解码（与本文件其它 LLM 调用一致）。
- 注意：如 §2 所述，这**不能完全消除**网关层不确定性。

## 3.5 复赛 −44.7 万事故的根因与本轮修复（语义接地 + fail-safe + 历史自检）

### 事故现象
复赛两位未知司机：偏好扣分 **52.6 万** → 净收益 **−44.7 万**，token 烧到 289 万。

### 根因（已定位）
- 526,100 ÷ (2 司机 × ~92 天) ≈ **2,859/司机日**，恰是"一条**每日生效**约束被几乎每天违规一次"的量级；
  夜休罚金 2,700/次 × 92 × 2 ≈ 49.7 万，与之吻合 → **最大头是夜间停车休息几乎每天被违规**。
- 机制：偏好处理是 **LLM 抽取 → 关键词/子串"接地"校验 → 确定性调度执行**。
  老的接地是**写死关键词白名单**：`no_drive_windows` 必须原文**同时**命中时间词+动作词
  （`_ndw_grounded()`），否则**整条静默丢弃**；`forbidden_categories/regions`、`blackout`、
  `avoid`、`monthly_category_targets` 用 `_text_supports()` 原词子串匹配接地。
- 复赛偏好是自然语言、措辞会变："入夜收车""后半夜不揽货""天黑归家落锁"等没进白名单的说法
  → LLM 即使抽对了夜休窗口也被**静默丢掉** → 调度器以为没有夜休 → **每天整夜出车，按天复利扣到 50 万**。
- 关键不对称：**漏一条"每日生效"约束 ≈ 25 万/司机；多一条最多损失几小时收入**。老逻辑"宁可漏不可错"方向反了。

### 本轮修复
- **P0 时间窗 fail-safe**：`_merge_llm_rules` 里**删除 `_ndw_grounded()` 关键词门**，
  直接采纳 temperature=0 抽出的 `no_drive_windows`（含跨夜 start>end），只做时刻合法性校验。
  decision system prompt 里写死的 "21:00–06:00 夜停休" 文案改为**通用措辞**（不同司机时段不同），
  实际时段来自解析结果。解析 prompt 强化：任何"入夜/天黑/后半夜…不出车/收车/归家不动/熄火"
  一律填 `no_drive_windows`（+ 含休息含义则同时填 `rest_window`）。
- **P1 语义接地**：新增 `_confirm_rule_holds(rule_desc, all_text, default=True)`——
  用一次 temperature=0 的 LLM 调用判断"原文是否确实施加该约束"，**只有模型明确说"否"才丢弃，
  调用失败/不确定一律保留（fail-safe）**；带缓存。替换 `no_drive_windows / forbidden_categories /
  forbidden_regions / blackout / avoid_categories / monthly_category_targets` 的子串/关键词接地。
  → 任意措辞都能泛化，根治"换个说法就丢规则"。（`allowed_regions / bounded_area / forbidden_zones`
  这类"误加危害更大"的字段**仍保留原有保守门**，未放宽。）
- **P3 历史自检**：`_compliance_self_audit()` 每天把司机的硬时间窗（休息/禁驶）作为
  "【硬约束·每日生效】"块置于决策 prompt 顶部，并扫描滚动历史，若**昨日**有在禁驶时段出车的记录
  就追加"【历史自检】昨日违规"提醒。纯历史查询、无额外 LLM 调用；因为罚分按天复利，
  抓到一次即可阻止后续每天重犯。

> 验证建议（本地无复赛司机数据）：自造"措辞刁钻"的夜休/禁区偏好喂进解析器，
> 看日志 `parsed rules ... no_drive=...` 是否被采纳即可，几秒出结果，不必跑满月。
> 满月跑分受 §2 网关不确定性影响，需多跑取均值。

## 3.6 架构改造：每日合规计划器（raw-NL 为第一公民，按天具象化）

### 动机（针对复赛未知司机扣分多的根因）
老架构是「**一次性** NL→固定 schema 解析 → 硬编码调度执行」。它有两个结构性短板，
正好打在复赛（广东 + 江浙沪两位未知司机、措辞与本地 D001 不同）的痛点上：

1. **schema 表达力上限**：固定字段（`no_drive_windows`/`rest_window`/品类指标…）
   表达不了**日历条件式**偏好——例如 D001 的"周末两天可以晚两个小时再休息"、
   "某月指标 + 上月欠额结转"。本地评分器 `calc_monthly_income.py` 明确按
   星期判定（工作日 21:00 / 周末 23:00 起夜休），而静态窗口是"每天一样"的。
   未知司机的此类条件式偏好要么解析丢失（按天复利扣分），要么只能全月最保守
   执行（白白损失收入）。
2. **一次性解析的脆弱性**：解析错一次，错整个赛季；没有任何按日重新对照
   偏好原文的机会。

### 新架构（三层）
全部改动仍集中在 `demo/agent/model_decision_service.py`：

1. **静态解析层（兜底，保留）**：原 LLM 解析 + 正则补充，产出 DriverRules。
   现在只作为**保守下限**，不再要求 schema 覆盖一切。
2. **每日合规计划层（新增，核心）**：`_ensure_daily_directive()` 每个仿真日
   一次小调用（temperature=0，max_tokens=300，按天缓存、失败最多重试 2 次），
   输入是**偏好原文 + 单条罚款金额 + 今天的公历日期/星期 + 月度品类/长途进度**，
   输出"今天"的具体约束：
   - `no_drive_today`：今日（含跨入明晨）禁驶时段；
   - `replaces_default`：今天的时段是否**替代**平日默认（如周末晚 2 小时）；
   - `today_plan` / `category_focus`：今日要点与优先品类，注入决策 prompt。
3. **确定性执行层（改造）**：所有守卫（`_hard_order_deadline` /
   `_interval_overlaps_no_drive` / `_extend_wait_for_no_drive` / `_safe_wait` /
   `_safe_reposition` / `_validate_llm_take_order` / 调度器 D3 / 合规自检）改用
   `DriverRules.no_drive_windows_for(day)` 的**有效禁驶窗**强制执行。

### 合并语义（不对称风险设计）
- 默认**取并集**（静态窗 ∪ 当日计划窗）：漏一条"每日生效"窗 ≈ 每天扣一次、
  全季 25 万级；多一条最多损失几小时收入 → 加窗永远 fail-safe。
- `replaces_default=true` 才允许**替换**静态窗（用于周末放宽这类合法放松），
  且仅当**每个静态窗都与某个计划窗相交**（即每条既有约束都被"认领"、只是
  改了形状）才生效；否则自动退回并集。LLM 永远无法静默删除一条既有约束。
- 计划层任何失败（模型不可用/输出不可解析）→ 当天退回纯静态规则。

### 收益
- **扣分**：未知措辞/条件式偏好按天重新对照原文具象化，不再依赖 schema 命中；
  即使静态解析整条丢失，计划层窗口照样被确定性强制（见
  `tests/test_daily_directive.py::test_directive_only_window_is_enforced_by_guards`）。
- **得分**：周末/特定日合法放宽被利用（如 21:00→23:00 多 2 小时接单窗）。
- **token**：~1 次小调用/司机日 ≈ 92 次 × (约 0.8k prompt + 0.2k completion)
  ≈ 10 万 token/司机，相对 500 万上限可忽略。

### 测试
`python demo/tests/test_daily_directive.py`（11 项：合并/替换/拒绝替换语义、
窗口换算、按天缓存与重试上限、失败回退、守卫强制、周末放宽）。
原有 `test_overnight_rest_window.py`、`test_longhaul_cap_history.py` 全部保持通过。

## 3.7 相反偏好加固：去掉最后一处 D001 偏置 + 镜像规则字段

### 动机
复赛司机的偏好可能与 D001 **方向相反**（不是禁止某事，而是只做某事/必须做某事）。
审计发现三处会让这类司机吃罚分或被错误压制：

1. **长途上限是全局常量**（最严重）：`LONGHAUL_CAP=5` 来自 D001 的偏好，却被无条件
   套到所有司机——决策 system prompt 写死"每月长途软上限5单"、`_validate_llm_take_order` /
   `_pick_order` 主动压制第 6 单起的长途。专跑长途或有"长途配额"偏好的司机会被
   全季节流 → 欠单按次罚，3 个月可达 10W+。
2. **品类只有黑名单**：schema 无品类白名单，"只拉水果"这类偏好无法结构化 →
   确定性调度照接其他货，按单扣。
3. **干线距离只有上限**：无 `haul_min_km`，"低于X公里短活不接"无法结构化。

### 修复
- **长途上限改为偏好驱动**：新增解析字段 `monthly_longhaul_cap{max_orders,min_hours}`
  （+离线正则兜底可解析 D001 原文），存到 `DriverRules.longhaul_cap_orders/longhaul_min_minutes`，
  罚金走 `rule_penalties["longhaul_cap"]`。所有执行点（验单/择单/prompt 展示）改为
  **仅当该司机解析出上限时**才生效；决策 system prompt 删除写死的"5单上限"，
  并明确"没列出的限制就不存在，不要自行假设"。
- **新增 `allowed_categories` 品类白名单**："只拉/只接X"。两个方向都有代价
  （误加→全面节流；漏掉→按单罚），所以逐项语义确认（离线默认要求原文含
  只/仅/专/除了等白名单标记词）；执行端与 forbidden 同一套经济学（已知罚金→软成本，
  未知→保守硬拒）。
- **新增 `haul_min_km`**：haul_max_km 的镜像，两个评估器同点强制。

测试：`demo/tests/test_opposite_preferences.py`（10 项：无上限司机不被节流、
有上限司机软上限不变、解析/正则兜底/不臆造、白名单拒收与软成本、下限过滤）。

## 4. 仍然通用、未写死的既有设计（接手者可直接用）

- **偏好解析**：自然语言 → 结构化 `DriverRules`，按时间窗增量触发；
  支持品类指标、结转、禁运品类/区域、仅允许区域、空驶上限、每日接单上限、长途软上限等。
- **区域分组**：内置 广东/上海/江苏/浙江/安徽/江浙沪/**长三角**/珠三角/大湾区 + 别名归一，
  广东与长三角司机都能覆盖（`_ALLOWED_REGION_GROUPS`）。
- **长途软上限**：`_score_item()` 里对 >8h 且已达上限的单 `eff_net = net − LONGHAUL_PENALTY`，
  净收益为正才接 → 天然实现"毛高带点罚也接"。
- **历史驱动的权威计数**：`_sync_monthly_counts_from_history()` 每步用
  `query_decision_history` 重建月度长途/品类/空驶/接单累计，保证额度判断准确
  （因为 harness 不回调结果）。

## 6. 给接手 agent 的下一步建议

1. **任何调优都多跑几次再下结论**（§2）。
2. 想进一步抬高"下限"，可考虑：当确定性调度 `_pick_order` 已找到强净值订单时，
   不让 LLM 把它改成 wait/reposition（减少 LLM 把好货等没的坏样本）。
3. 复赛若出现新的品类/结转/区域偏好，确认**偏好解析器**能从自然语言抽出来即可，
   不要再往决策逻辑里加写死分支。
