## -18. 压罚分 v9：多夜穿越额外保证金（`AGENT_NIGHT_CROSS_EXTRA_MARGIN_PER_DAY` 0→1.0）

**触发**：用户要「精准提分 / 在 84949 最高基础上削一些罚分」。我们 17800 比 #2/#3 的 10100
多 7700——光把罚分压下来就近乎白送净分（毛收入一分不用涨）。

**为什么选这把刀（机制 + 证据）**：
- **机制是候选过滤，对 LLM 是硬约束**：决策 LLM 不是自由选 cargo——它只能从
  `_evaluate_cargo` 返回非 None 的候选里挑（`model_decision_service.py` 构建喂给 picker /
  LLM 的 `cargo_summary`）。夜穿越单若净收益不达保证金，`_evaluate_cargo` 直接 `return None`，
  从列表里删除。所以**收紧保证金 = LLM 根本看不到、选不了那批单**，不是靠 prompt 自觉。
- **证据**：思考 A/B（§-6/§-7）——思考开毛收入↑但罚分翻倍（45100 vs 24400），机理正是 LLM 被
  推去接带罚分的大单；而多夜穿越单是其中「罚分/毛利」最差的一档（每多跨一晚都多吃一次满额夜罚
  ＋次日压缩等被单罚模型低估的隐性成本，§-3）。

**改动**（`model_decision_service.py`，纯默认即生效）：
`_NIGHT_CROSS_EXTRA_MARGIN_PER_DAY` 默认 `AGENT_NIGHT_CROSS_EXTRA_MARGIN_PER_DAY` **0→1.0**。
逻辑：穿越 >1 晚时，在基础 `_NIGHT_CROSS_MARGIN` 之外再要求
`night_pen * 1.0 * (crossings-1)` 的额外无罚净收益。所以一张 2 晚穿越单的门槛 ≈
`night_pen*crossings*(1.5-1) + night_pen*(crossings-1)` = **双倍 night_pen**（base 2700→需净 5400）。

**精准 + 安全的关键：只砍多夜，单夜不动**。`crossings == 1` 的傍晚大单在任何取值下都**不经过**
这一项（代码 `if ... and crossings > 1`），逐字节不变——合规穿越的主体（单夜傍晚肥单）完全保留，
所以毛收入损失被夹在「极少数 2+ 晚边际单」上。

**诚实框定**：不是纯 no-op——被删的多夜单万一其真实净值为正，会掉一点毛收入。但这批单按 §-3 的
论证普遍是**真实成本 > 所计罚分**（被低估），删掉多半是 +EV；且 best-of-N 下 84949 永久保底。
**回退一行**：`AGENT_NIGHT_CROSS_EXTRA_MARGIN_PER_DAY=0`。

**精准化的下一步（仍待用户）**：要真正打中最大那项罚分，需要 `monthly_income_202603.json` 的
`preference_check` 各规则罚分明细。若大头其实是**品类指标欠达标**（少跑水果/建材），方向要反过来
（更积极接该品类），这把刀就打偏——用户暂时看不到/不找明细，故先上这把证据最强的安全刀。

**平台验证**：纯默认多跑取均值，盯**罚分↓？毛收入有无明显回吐？net 净效果？** 若罚分降而毛收入
基本没掉 → 成功，可考虑再上 `_NIGHT_CROSS_MARGIN` 1.5→1.8 这档更广的；若毛收入回吐过多 → 回退 0。

**测试**：`test_evening_bigorder_crossing.py` 新增 `test_extra_margin_per_day_default_is_active`
（守护默认≥1.0）、`test_two_window_crossing_trimmed_by_extra_margin`（同一 2 晚单 extra=0 接、
默认 1.0 删）、`test_huge_two_window_crossing_survives_extra_margin`（巨单仍接）、
`test_single_window_crossing_unaffected_by_extra_margin`（单夜不受影响）；

`test_extra_margin_default_trims_thin_multiday`（断言新默认会削薄多夜单）。v9 独立分支基于 master 时 **148 项全绿**；并入 #89 的 3 项上下文宽度守护后 **11 文件 / 151 项全绿**。

## -17. 攻毛收入 v8：加宽决策 LLM 上下文（候选 24→40、市场表 12→20）

**安全的「更好利用 LLM」方向 = 花在信息量，不是推理深度**：每步只给决策 LLM 看

## -15. 攻毛收入 v6：弱单换位阈值 45→58（与罚分正交的最稳一步）

**为什么 §-13 的「按构造扣分中性」是错的（重要教训，已同步进 AGENTS.md）**：
- `_candidate_rank_score` 的输入 `eff_net` 是**已减软罚分的净值**，所以「在 net>0+合规过滤之后重排」
  这句话本身没错——错在把它等同于「扣分中性」。
- `net>0＋合规过滤`**只挡硬违规**（硬禁驶窗口、硬时窗冲突等）。带**软罚分**的单（长途上限溢出、

- chain_depth / chain_near 是**毛收入向的乘子**（恒 ≥1），它们偏好「卸货落在/紧挨旺枢纽」的目的地。
  这类目的地往往对应**更长、更晚的大单**（去大枢纽=长途+常跨夜）。乘子足够大时，会把一个
  `eff_net` 已被软罚分压低、但落点旺的大单，**抬到一个清白小单之前**。于是 agent 系统性地
  多接长途/夜穿越/品类溢出单 → 扣分暴涨，而抢来的毛收入又被里程成本和罚分吃掉、毛收入也没涨。
- 一句话：**「重排已过过滤的候选」≠「扣分中性」**。只有当被重排维度与罚分**正交**时才中性；
  而「落点流动性」与「单子长度/时段/品类」高度相关，并不正交。今后任何价值向杠杆的扣分影响
  都当作**平台 A/B 的实证问题**，不能再当成构造性保证。

## -11. 攻毛收入 v3：链路「深度」加成（`AGENT_CHAIN_DEPTH_WEIGHT`）

**背景**：§-7 已确认唯一大头差距是毛收入（我们 ~96k vs 榜首 132k），且扣分已是全场第 5 低——

"卸到旺城就地再装、少空驶"，但它只用卸货城的**均价** net/h（`_cargo_liquidity_stats` 的 `s/n`），
**忽略了市场深度**：一个"均价高但只有 1 条货"的城市，链一次就断、卡车仍要空驶；一个"均价中等
但有几十条货"的枢纽，才是可靠的即时回装点。把深度也计入排名是一处**未挖的纯毛收入杠杆**。

**本轮改动（一处，`_candidate_rank_score`；按构造扣分中性、默认 no-op）**：
- 新增 `AGENT_CHAIN_DEPTH_WEIGHT`（默认 **0=关**）与 `AGENT_CHAIN_DEPTH_REF`（默认 **8**）。
- 在既有链路均价乘子之外，再叠加一个**深度乘子** `1 + w · min(1, ln(1+n)/ln(1+ref))`，其中
  `n` = 该卸货城近窗口内观测到的在架货源条数（同一 `_cargo_liquidity_stats` 表，零额外仿真/网络
  开销）。对数缩放、在 `ref` 条饱和，**绝不降低分数**（乘子 ≥ 1）。
- **仅对**已 `chain_liq>0`（卸货城本身有正流动性）的目的地生效——深度不能救一个"会困死卡车"的

**测试**：`test_balanced_value_layer.py` 新增 3 项（默认 0 时供深度计数为严格 no-op；开启后等净值+

## -10. 动态检索 few-shot（`AGENT_FEWSHOT_TOPK`）：≥400 条示例库 + 解析时注入 top-K

**背景（诊断）**：2026-06-14 榜单显示我们排名垫底（nchu 净 64478，全场最低）。把各队
「毛收入−里程成本」(=净分+扣分) 拆出来看，**我们 95778 是全场最低**，而扣分 31300 反而是
全场第 5 低——瓶颈是**毛收入不是扣分**。根因是**过度保守**：偏好抽取器**臆造**了输入里并不
存在的约束（夜禁窗、禁区、品类禁令…），导致无谓躲单 → 毛收入垫底。强队靠「喂大量 few-shot」
把抽取做稳；但**内联几百条** few-shot 有三重风险：① 单次上下文窗口被占满（11 万 token 量级）；
② lost-in-the-middle + **诱导过度抽取**（模型为对齐示例硬凑约束）——正好放大我们的根因；
③ 反复抽取吃 4h 墙钟。所以采用**动态检索**：覆盖=400+，但每次只注入最相关的 ~40 条。

**本轮改动**：
- 新增示例库 `demo/agent/parse_fewshot_bank.py`：**411 条**示例（≥400），由**参数化模板生成**——
  每条的 `入`文本与 `出`JSON **同源产出**，标注 100% 正确（不靠手敲）。覆盖全部 27 个 schema
  字段 × 方言（粤/吴/客家/口语）× **59 条「零约束/钓鱼」反例**（闲聊、"想多挣钱"这类愿望、
  提到但未禁止——全部 → 空/默认 JSON，专治过度抽取）。原内联的 22 条精选示例**原样移入**库中作种子。
- **纯 Python 检索器**（无网络/无 embedding/无 numpy）`select_examples(query, k, n_anchor)`：
  对每条偏好文本按**中文字符 bigram 余弦相似度 + 领域关键词/方言命中加权**打分，取 top-K；
  并**固定预留 `n_anchor` 个 anchor 反例槽**，使「别过度抽取」的信号每次必到。确定性排序
  （分数降序、index 升序）⇒ 同 query 同结果。
- **接线**：`_PARSE_SYSTEM` 瘦身为「规则头（保留"偏好抽取器"字样）+ 27 字段定义 + 13 条规则」，
  内联示例删除；`_llm_parse_preferences` 改为 `system = _PARSE_SYSTEM + _fewshot_block(texts)`，
  `_fewshot_block` 调检索器把 top-K 以原 `入/出` 格式拼接。抽取仍是**每条偏好调一次**，
  检索按该条文本定向。
- 新旋钮 `AGENT_FEWSHOT_TOPK`（默认 **40**，**0=禁用检索**走纯规则头提示）。仅在 `AGENT_PARSE_LLM=1`
  时生效。库导入加 try/except 兜底（不可用则退化为无示例，绝不崩）。

**token 账**：few-shot 仅存在于抽取 system prompt、**每条偏好一次**。每条示例 ≈270 token，
K=40 ≈ 1.08 万 few-shot token / 次抽取，整 prompt ≈ 1.37 万 token / 次。配合 `AGENT_DECISION_LLM=0`
省掉 ~200 万/司机的每步决策 token 后，每司机总花费 ~200 万 → **~30 万（约 3M 预算的 10%）**。

**测试**：新增 `demo/tests/test_parse_fewshot_bank.py`（14 项）：全库 JSON 合法 + 键 ∈ 27 字段、
库 ≥400、含反例与 anchor、检索相关性（夜休/品类查询命中对应字段）+ 有界（≤k）+ 确定性 +
anchor 必含、`AGENT_FEWSHOT_TOPK=0` 返回空、组装提示仍含"偏好抽取器"（保证既有 mock 路由不破）。
全仓回归 **11 文件 / 135 项全绿**（原 121 + 新 14）。

> **建议的 A/B 提交**：`AGENT_DECISION_LLM=0 AGENT_PARSE_LLM=1 AGENT_FEWSHOT_TOPK=40`
> （纯确定性调度 + 检索式重 few-shot 解析），与默认版按 §2 各多跑取均值对比。单跑不可比
> （§2 网关非确定性）。回退：`AGENT_FEWSHOT_TOPK=0`（退回纯规则头，无检索），或调小 K 降 token。

### E1. 默认关闭决策思考模式（`AGENT_DECISION_THINKING` 默认 1 → 0）

  把算力转向"每步快速调用 + 更宽上下文"——对齐榜首的高 token / 快速决策画像。
- 选择性思考的全套机制（§-5 的累计上限/配速/高价值闸）**原样保留**，只是不再默认触发；
  想恢复旧思考路径设 `AGENT_DECISION_THINKING=1` 即可（行为与 §-5 完全一致）。

### E2. 加宽快速模式下的决策上下文（把闲置 Token 花在 throughput 上）
- `AGENT_LLM_CARGO_SUMMARY_LIMIT` 默认 18 → **24**（每步给 LLM 看更多已过合规检查的候选货）。
- `AGENT_LIQ_TOP_N` 默认 8 → **12**（【活跃市场】表更宽，利于更优的接力/空驶选择）。
- 二者都只是**prompt 列表长度**，不碰任何可行性过滤或合规守卫；候选仍按 `_candidate_rank_score`
  降序、LLM 仍只能在合规候选里选。提交时 token 仅用了上限的 ~21%（§-1.1），榜首用到 ~3.08M/司机，
  所以加宽上下文是把这段闲置预算转成"更聪明的快速决策"的最便宜杠杆 → 攻毛收入。

### E3. 攻毛收入（只动"合规前已过滤"的价值排名/择单层，按构造扣分中性）
用户诉求"更多毛收入 + 合理一点扣分"。所有夜穿越/多日穿越等"拿扣分换毛利"的 knob **一律不动**
（扣分由确定性合规层硬守、§-6 关思考已把扣分往回压），只推**对扣分中性**的三个毛收入杠杆——
它们都只对**已过 `net>0` 可行性 + 合规检查**的候选重排序/择单，绝不放宽任何约束、绝不新增违规：
- `AGENT_ABS_NET_ALPHA` 默认 **0 → 0.2**：`_candidate_rank_score` 叠加绝对 net 的对数项，
  把大单从"被略快的小单埋掉"里捞回到列表/择单前列（§-2 诊断的"最大单没接到"头号根因，
  此前默认关）。快速 LLM 与确定性 `_pick_order` 同用此分。
- `AGENT_CHAIN_VALUE_WEIGHT` 默认 **0.3 → 0.45**：更看重卸货城市的接力流动性，卸到旺城就地再装、
  少空驶 → 整条链全天毛收入更高（卸货城无观测流动性时该项中性）。
- `AGENT_LLM_WAIT_OVERRIDE_NET_PER_H` 默认 **60 → 50**：LLM 想长等而桌上已有 ≥50元/h 的**合规**单时
  直接接单——把"等更好的货"这类毛利泄漏再收紧一档（接的都是已过合规的单，不增扣分）。

测试：`test_selective_thinking.py` 新增 `test_thinking_off_by_default_even_on_big_net`（验证默认即便
大单步也跑快速：无 `enable_thinking`、completion=180、不计思考预算）；原先依赖"默认开思考"的三项用例

> 回退毛收入档（E3）：`AGENT_ABS_NET_ALPHA=0 AGENT_CHAIN_VALUE_WEIGHT=0.3 AGENT_LLM_WAIT_OVERRIDE_NET_PER_H=60`。

## -5. 复盘最新提交 → 选择性思考（用满闲置算力）+ 多日穿越加罚边际（扣分↓）

**诊断（两条可改进线）**：
1. **思考预算几乎没花到**：决策耗时仅 **2.91s** ≈ 快速模式（思考真跑时实测 ~22s/步，§-1.2）。

   "还有 ~7-8M token 没用"。根因是 §-1.2 的墙钟保险是**永久关闭式**：开季 `sim_frac` 极小时，

2. **多日穿越把扣分从 25k 抬到 31.3k**：§-4 的 A2 放开了"跑过夜窗进入次日"的多日穿越

**本轮改动（仍全部 env 可调；合规硬守卫一律不动；默认值是保守起点，须按 §2 在官方平台多跑标定）**：

### D1. 选择性思考（把闲置 token/墙钟花在"该思考"的决策上，且永不触 4h 红线）
把"永久关闭式"墙钟保险改成**逐步自调节 + 高价值才思考**（`AGENT_THINKING_SELECTIVE`，默认开；设 0 回退旧永久关闭逻辑）：
- **(a) 硬累计上限**：每司机累计思考墙钟 `self._thinking_spent` **永远** ≤ `AGENT_THINKING_WALL_BUDGET_SECONDS`（默认 6600s/司机）

- **(b) 自调节配速**：允许思考的额度随仿真进度 `sim_frac` 增长（`spent > budget × sim_frac` 时本步先跳过思考），
  超前就暂停、落回线下自动恢复——不像旧逻辑超一次就**永久**死掉，于是预算被**均摊到整季**而非开季烧光。

- LLM 介入深度**不变**（本来就每步调用决策 LLM，§-1.1）——选择性思考只决定**这次已发生的调用是否带 `enable_thinking`**，

  再要求 `net > night_pen × extra × (crossings − 1)` 的免罚净值。
- `crossings == 1`（单日穿越）**完全不受影响**；`extra == 0` 时整支闸**等价于旧逻辑**（零回归）。
- 平台上把它调 >0，即可**只**砍掉 §-4 抬高扣分的那批边际多日穿越，而不硬拒真正巨利的多日大单——
  把扣分往回压而尽量不伤毛利。

测试：新增 `demo/tests/test_selective_thinking.py`（11 项：大单/品类压力触发思考、低价值步保持快速、

## -4. 平衡利弊总优化（A 攻毛利 / B 软违规 / C 用满算力）

在 §-3 安全边际的基础上，按"毛利↑、把硬拒转成可盈利软违规、用满闲置算力"三条线做一轮
**全部 env 可调**的优化（最优值仍须按 §2 在官方平台多跑取均值/下限标定；本地只能验证机制
正确性，不能验证净效果）。所有合规硬守卫（`_validate_llm_take_order` / `_safe_*` / 战略闲置守卫）
**一律不动**——LLM 永远不能放宽约束。

### A. 接单（毛收入，最大杠杆）
- **A1 链路价值排名**（`_candidate_rank_score`）：在"开销摊销 net/h"之上叠加**绝对 net 对数项**
  （`AGENT_ABS_NET_ALPHA`，默认 0）与**卸货城市接力流动性**（`to_liq`，`AGENT_CHAIN_VALUE_WEIGHT`，
  默认 0.3）。确定性 `_score_item` 与 LLM 候选排序同用；卸货城市无观测流动性时该项中性，
  绝不改变 `net>0` 可行性过滤。
- **A2 跨夜大单多日穿越**（`_count_nodrive_crossings`）：超长途可跑过夜窗尾进入次日，
  按**每穿越一个夜窗计一次当日夜罚**（不再硬拒），上限 `AGENT_NIGHT_CROSS_MAX_DAYS`（默认 2）+
  月界；仍 fail-safe（未知罚金硬拒）+ 仍受 §-3 安全边际 `_NIGHT_CROSS_MARGIN` 约束。
  这放开了此前被硬拒的"利润最高的超长途"。
- **A3 弱单换位**（默认关）：本地最优单 net/h 低于 `AGENT_WEAK_LOCAL_REPOSITION_NET_PER_H`（默认 0=关）
  时，转去 `_anti_strand` 朝更旺的实测市场空驶；带 `min_net` 闸——只有目标锚单净值**严格高于**
  本地单才换，绝不拿确定的单去换更差的。

### B. 偏好（把"硬拒"转成"可盈利的软违规"）
- **B1 penalty_cap 兑现**：解析新增**按规则累计扣款上限** `rule_penalty_caps → DriverRules.rule_caps`。
  某规则本月累计罚已触顶后，边际违规成本为 0（评分器也封顶），于是停止计价、解锁被它挡掉的单：
  - 夜窗穿越：从权威历史重建 `monthly_night_violations`（"当天有在窗内行驶"的去重天数——
    是评分器违规条件的**子集**，绝不会**多**记 → 绝不会提前误兑现），触顶后 `_evaluate_cargo` 免罚穿越；
  - 长途软上限：`_longhaul_cap_credit` 触顶后免罚。
  `AGENT_PENALTY_CAP_CREDIT`（默认开）；无 cap 的司机（如本地 D001）完全无影响。
- **B2 品类紧急软化**：紧急配额期不再把非品类大单一律跳过；当其 `net > 单次品类欠单边际罚`
  时照接（仅在罚金已知时，未知则保守继续猎品类）。`AGENT_CATEGORY_SOFT`（默认开）。
- **B3 更多软成本**：解析同时归因 `rule_penalty_caps`，让更多约束从"未知罚金→硬拒"变成"已知罚金→软成本"。

### C. 用满闲置算力（Token/思考预算）

  按仿真进度折算的保险仍会在 4h 前硬停，故只是花掉本就闲置的墙钟。

## -3. 价值层回吐复盘 → 夜穿越安全边际（攻"扣分涨得比毛利还多"）

| §-2 之前（本队最优） | **59587** | 25000 | 84587 | 2.18M | 3.39s |

净收益反而 **−10.2k**。即"用扣分换毛利"换亏了。注意两点：
1. **绑定约束是 4h 跑时上限，不是 token**。决策耗时仅 3.13s ⇒ thinking 已被墙钟保险

- **`margin == 1.0` 完全等价于旧逻辑（net>0）**；`margin > 1.0` 严格只接旧逻辑的**子集**
  ⇒ 只可能**减少**穿越次数 ⇒ 夜间扣分单调下降。真正的大单（净 ≫ 夜罚）照接，保留 #76 初衷。
- 非穿越单（白天/不进夜窗）行为完全不变；只对"赴装在窗前、干线finish进同一夜窗"的穿越生效。

## -2. 排行榜复盘 → 价值层优化（攻"过度保守、大单没接到"）

推掉了"。夜休罚是**按天计**，一笔净 > 当日罚的大单就该接。Token 仅用预算 21%，
价值侧（选单/接力）还有大量算力没花。**该用扣分换毛利**：+2 万扣分换 +4.2 万毛收入净赚。

**本轮改动（全部在 `demo/agent/model_decision_service.py`，只增不减毛利 / 不放宽任何合规闸门）**：

1. **选单目标函数：绝对净收益加权（最大杠杆）**。旧 `_score_item` 用纯 `net/分钟`
   排序，会把"占 10h、净 5000(8.3/min)"的大单排在"占 1h、净 600(10/min)"小单之后——
   正是"大单没接到"的头号根因。新增 `_amortized_rate(net, occupied)`：把一笔**固定
   非生产开销** `_ORDER_TIME_OVERHEAD_MIN`（默认 60min＝扫描+赴装+单间空等的摊销，
   env `AGENT_ORDER_TIME_OVERHEAD_MIN` 可调）摊进时间分母 → 大单的相对排名回升，
   倾向"少而大"的接单结构。**绝不接亏损单**（`net>0` 过滤不变，仅对已可行候选重排序）。
2. **决策 LLM 候选增强（用闲置 token 创造价值）**。候选行新增**绝对 `net`**（原来只有
   `net_per_h`），候选列表改按 `_amortized_rate` 降序（大单排在模型先读到的位置），
   system prompt 选货指引改为"①绝对净收益 net → ②效率 net_per_h → ③接力价值 to_liq"
   并提示"有充足思考预算可据 to_liq 预判接力后续 1-2 单"。候选条数 12→18、活跃市场
   表 6→8（env 可调）。LLM 仍只能在**已过合规检查**的候选里选，护栏不变。
3. **战略闲置阈值放宽**：`_LLM_WAIT_OVERRIDE_NET_PER_H` 80→60（env 可调）。LLM 想长等
   而桌上已有 ≥60元/h 的合规单时直接接单——压扣分式的"等更好的货"本身就是毛利泄漏。

测试：新增 `demo/tests/test_value_optimization.py`（7 项：摊销排名翻转 / 选单偏好大单 /
LLM 候选含绝对 net 且大单排前 / prompt 含绝对净收益指引），既有 76 项全部保持通过（合计 83）。

## 0. 当前架构：闭环偏好编译（面向未知司机泛化）

复赛是两位未知司机（广东 / 江浙沪），偏好为措辞会变的自然语言；旧架构靠
「按 D001 措辞写死的正则补抽 + 关键词白名单接地」做召回，换个说法就漏规则 →
按天复利扣分。新架构（全部在 `demo/agent/model_decision_service.py`）：

1. **逐条编译（LLM 优先）**：每条偏好**单独**调用一次抽取 LLM（不再把全部偏好拼一起批量抽），
   语义接地校验只对照该条原文，互不串扰；新偏好出现时只编译新条目（省 token、免重复合并）。
2. **审计修复（闭环，取代正则补抽层）**：编译后用一次 LLM「覆盖审计」——
   逐条核对偏好原文的全部约束是否都体现在结构化规则清单里（`_audit_preference_coverage` +
   `_describe_rules_for_audit`），缺失部分以**补丁**形式回填（仍走 `_merge_llm_rules` 的接地校验）。
   旧的 `_supplement_basic_rules` / `_supplement_dated_events` 等正则补抽只在**模型不可用**时作为离线兜底。
   （夜休 fail-safe `_supplement_night_failsafe` 因属灾难性规则的最后保险，仍保留。）
3. **零静默丢弃（residual 通道）**：审计后仍无法用结构化字段表达的偏好（如「下雨天不接生鲜」这类
   条件型约束）进入 `DriverRules.residual_constraints`，连同违约金额逐步注入决策 prompt
   （`_format_rules_for_llm` 的【必须遵守·未结构化偏好】块 + `_compliance_self_audit`），
   由决策 LLM 在线遵守。任何偏好都不会被悄悄丢掉。
4. **语义接地全面替换关键词白名单**：`allowed_regions / forbidden_zones / bounded_area /
   must_visit / haul_max_km / daily_order_limit / home_rule` 的关键词门全部改为
   `_confirm_rule_holds` 语义确认；模型给出明确判定时**双向**生效（关键词没命中但语义确认成立
   → 采纳；关键词命中但语义确认不成立 → 丢弃），模型不可用时退回原关键词启发式。
   坐标类高危字段仍保留「原文必须出现显式坐标」的数据门。
5. **每日合规计划层（见 §3.6）**：在编译/审计之外，每个仿真日再用一次小 LLM 调用
   把偏好原文按当天日历（日期/星期/月度进度）具象化为"今日禁驶窗 + 今日要点"，
   守卫按"静态窗 ∪ 当日计划窗"强制执行——覆盖日历条件式偏好（周末时段不同、
   特定日期事件、月度结转）这类静态 schema 表达不了的情况。
6. **执行层**：确定性调度器继续保证已结构化偏好合规（含当日有效禁驶窗），并按净收益择单。

Token 影响：逐条编译 + 一次审计只发生在偏好首次可见时（每司机一次性数次调用），
相对决策循环（每 3 步一次）占比可忽略；逐条编译同时避免了旧版「出现新偏好时全量重抽」的浪费。

## 1. 业务背景与要求（来自仓库所有者）

- 本地数据集只有 **D001** 一位司机，仅用于自测。
- **官方复赛是两位司机**：一位**广东**司机，一位**长三角**司机。

## 2. ⚠️ 最关键的发现：单次跑分不可比（LLM 网关不确定性）

同一份代码、不同次运行，**净收益能相差 1 万以上**（毛收入在 ~88k–124k 间剧烈波动）。
实测（D001，满月 3–5 月）：

| 版本 | 采样温度 | 第1次 | 第2次 |
|---|---|---|---|
| 原版 agent（master） | 0.1 | 83.1k | 67.2k |
| 本优化（A+B1） | 0.1 | 79.2k | 58.0k |
| 本优化（A+B1） | 0   | 74.3k | 67.5k |

**结论**：
- 这种波动**baseline 自己也有**（67k–83k），是 **LLM 网关（qwen3.7-plus，疑似 MoE）固有的**，
  即使 `temperature=0` 也不能完全消除——不是 agent 代码能消掉的。
- 所以**用单次跑分去判断"某个改动有没有用"是不可靠的**。要比较必须**多次跑取均值/下限**。
- 复赛是**一次性两位司机**，真正该优化的是**抬高下限、降低波动**，而不是赌单次高分。

> 给接手者：如果你要继续调优，请**固定每个版本至少跑 3–5 次**再比较，否则会被噪声误导。

## 3. 本次关键改动（均在 `demo/agent/model_decision_service.py`）

### A1. 去掉 D001 专属硬编码（通用化）
- `_get_category_target()`：删除写死的 `if month_idx==1: 水果12` / `if month_idx==2: 建材12+进位`
  兜底分支。品类指标**只来源于从自然语言解析出的** `rules.monthly_category_targets`。
- `_track_category_order()`：删除只认 `=="水果"/"=="建材"` 的兜底，改为只按解析到的目标品类统计。
- 影响：对复赛未知司机不再错误地去抢"水果/建材"。D001 的品类指标本来就能被解析出来，行为不变。

### A2. LLM 目标对齐"净收益优先"
- system prompt 从"最大化净收入 / 最小化罚款 / 完成指标"改为**首要净收益**；
  接单提示从"高价、**短途**"改为"**净收益(net_per_h)最高**，长途只要 net_per_h 高也值得接"。
- 长途规则措辞改为**软上限**：超 5 单每单扣 1000，但该单净收益明显 > 1000 仍应接。

### A3. 喂给 LLM 的历史摘要改用"权威数据"
- 背景：评测 harness **只调用 `decide()`，从不回调 `update_decision_result()`**，
  所以 `DecisionHistory` 内部计数器恒为 0——原来摘要里一直显示"总接单 0 / 累计收入 ¥0 /
  最近订单全部 ✗"，**会误导 LLM**。
- 改法：`DecisionHistory.get_summary(current_day, plan)` 增加 `plan` 入参，
  累计/本月接单数、长途 x/上限、品类分布**改从每步重建的权威 `plan` 读取**
  （`plan` 由 `_sync_monthly_counts_from_history()` 用 `query_decision_history` 重建）。
  等待/空驶次数与"最近决策动作序列"仍来自本地滚动窗口（这些在 decide 时记录是可靠的）。

### B1. "欠额结转"对齐评分口径（重要！）
- 评分口径里：**四月水果欠额是用"五月水果"来补**的（`may_fruit_makeup_orders`）。
- 但原 `_get_category_target()` 的结转逻辑是把欠额加到**当月第一个品类（建材）**的目标上
  → agent 拼命多接建材（实测接了 21–23 单，远超 12），**对水果欠额毫无抵扣**，
  结果照吃 7000 的五月结转罚。
- 改法：结转时把上月每个品类的欠额加到**当月同一品类**的目标上
  （`targets[cat] += deficit`）。这样五月会去补**水果**，与评分口径一致。
- 该改动**只会更优或持平**：原逻辑给的结转抵扣credit为 0，新逻辑能真正抵扣。
  实测有一次 `mayMakeup=7` 成功把 7000 的五月结转罚降为 0。

### （附）主决策 `temperature: 0.1 → 0`
- 为可复现性改成贪心解码（与本文件其它 LLM 调用一致）。
- 注意：如 §2 所述，这**不能完全消除**网关层不确定性。

## 3.5 复赛 −44.7 万事故的根因与本轮修复（语义接地 + fail-safe + 历史自检）

### 事故现象
复赛两位未知司机：偏好扣分 **52.6 万** → 净收益 **−44.7 万**，token 烧到 289 万。

### 根因（已定位）
- 526,100 ÷ (2 司机 × ~92 天) ≈ **2,859/司机日**，恰是"一条**每日生效**约束被几乎每天违规一次"的量级；
  夜休罚金 2,700/次 × 92 × 2 ≈ 49.7 万，与之吻合 → **最大头是夜间停车休息几乎每天被违规**。
- 机制：偏好处理是 **LLM 抽取 → 关键词/子串"接地"校验 → 确定性调度执行**。
  老的接地是**写死关键词白名单**：`no_drive_windows` 必须原文**同时**命中时间词+动作词
  （`_ndw_grounded()`），否则**整条静默丢弃**；`forbidden_categories/regions`、`blackout`、
  `avoid`、`monthly_category_targets` 用 `_text_supports()` 原词子串匹配接地。
- 复赛偏好是自然语言、措辞会变："入夜收车""后半夜不揽货""天黑归家落锁"等没进白名单的说法
  → LLM 即使抽对了夜休窗口也被**静默丢掉** → 调度器以为没有夜休 → **每天整夜出车，按天复利扣到 50 万**。
- 关键不对称：**漏一条"每日生效"约束 ≈ 25 万/司机；多一条最多损失几小时收入**。老逻辑"宁可漏不可错"方向反了。

### 本轮修复
- **P0 时间窗 fail-safe**：`_merge_llm_rules` 里**删除 `_ndw_grounded()` 关键词门**，
  直接采纳 temperature=0 抽出的 `no_drive_windows`（含跨夜 start>end），只做时刻合法性校验。
  decision system prompt 里写死的 "21:00–06:00 夜停休" 文案改为**通用措辞**（不同司机时段不同），
  实际时段来自解析结果。解析 prompt 强化：任何"入夜/天黑/后半夜…不出车/收车/归家不动/熄火"
  一律填 `no_drive_windows`（+ 含休息含义则同时填 `rest_window`）。
- **P1 语义接地**：新增 `_confirm_rule_holds(rule_desc, all_text, default=True)`——
  用一次 temperature=0 的 LLM 调用判断"原文是否确实施加该约束"，**只有模型明确说"否"才丢弃，
  调用失败/不确定一律保留（fail-safe）**；带缓存。替换 `no_drive_windows / forbidden_categories /
  forbidden_regions / blackout / avoid_categories / monthly_category_targets` 的子串/关键词接地。
  → 任意措辞都能泛化，根治"换个说法就丢规则"。（`allowed_regions / bounded_area / forbidden_zones`
  这类"误加危害更大"的字段**仍保留原有保守门**，未放宽。）
- **P3 历史自检**：`_compliance_self_audit()` 每天把司机的硬时间窗（休息/禁驶）作为
  "【硬约束·每日生效】"块置于决策 prompt 顶部，并扫描滚动历史，若**昨日**有在禁驶时段出车的记录
  就追加"【历史自检】昨日违规"提醒。纯历史查询、无额外 LLM 调用；因为罚分按天复利，
  抓到一次即可阻止后续每天重犯。

> 验证建议（本地无复赛司机数据）：自造"措辞刁钻"的夜休/禁区偏好喂进解析器，
> 看日志 `parsed rules ... no_drive=...` 是否被采纳即可，几秒出结果，不必跑满月。
> 满月跑分受 §2 网关不确定性影响，需多跑取均值。

## 3.6 架构改造：每日合规计划器（raw-NL 为第一公民，按天具象化）

### 动机（针对复赛未知司机扣分多的根因）
老架构是「**一次性** NL→固定 schema 解析 → 硬编码调度执行」。它有两个结构性短板，
正好打在复赛（广东 + 江浙沪两位未知司机、措辞与本地 D001 不同）的痛点上：

1. **schema 表达力上限**：固定字段（`no_drive_windows`/`rest_window`/品类指标…）
   表达不了**日历条件式**偏好——例如 D001 的"周末两天可以晚两个小时再休息"、
   "某月指标 + 上月欠额结转"。本地评分器 `calc_monthly_income.py` 明确按
   星期判定（工作日 21:00 / 周末 23:00 起夜休），而静态窗口是"每天一样"的。
   未知司机的此类条件式偏好要么解析丢失（按天复利扣分），要么只能全月最保守
   执行（白白损失收入）。
2. **一次性解析的脆弱性**：解析错一次，错整个赛季；没有任何按日重新对照
   偏好原文的机会。

### 新架构（三层）
全部改动仍集中在 `demo/agent/model_decision_service.py`：

1. **静态解析层（兜底，保留）**：原 LLM 解析 + 正则补充，产出 DriverRules。
   现在只作为**保守下限**，不再要求 schema 覆盖一切。
2. **每日合规计划层（新增，核心）**：`_ensure_daily_directive()` 每个仿真日
   一次小调用（temperature=0，max_tokens=300，按天缓存、失败最多重试 2 次），
   输入是**偏好原文 + 单条罚款金额 + 今天的公历日期/星期 + 月度品类/长途进度**，
   输出"今天"的具体约束：
   - `no_drive_today`：今日（含跨入明晨）禁驶时段；
   - `replaces_default`：今天的时段是否**替代**平日默认（如周末晚 2 小时）；
   - `today_plan` / `category_focus`：今日要点与优先品类，注入决策 prompt。
3. **确定性执行层（改造）**：所有守卫（`_hard_order_deadline` /
   `_interval_overlaps_no_drive` / `_extend_wait_for_no_drive` / `_safe_wait` /
   `_safe_reposition` / `_validate_llm_take_order` / 调度器 D3 / 合规自检）改用
   `DriverRules.no_drive_windows_for(day)` 的**有效禁驶窗**强制执行。

### 合并语义（不对称风险设计）
- 默认**取并集**（静态窗 ∪ 当日计划窗）：漏一条"每日生效"窗 ≈ 每天扣一次、
  全季 25 万级；多一条最多损失几小时收入 → 加窗永远 fail-safe。
- `replaces_default=true` 才允许**替换**静态窗（用于周末放宽这类合法放松），
  且仅当**每个静态窗都与某个计划窗相交**（即每条既有约束都被"认领"、只是
  改了形状）才生效；否则自动退回并集。LLM 永远无法静默删除一条既有约束。
- 计划层任何失败（模型不可用/输出不可解析）→ 当天退回纯静态规则。

### 收益
- **扣分**：未知措辞/条件式偏好按天重新对照原文具象化，不再依赖 schema 命中；
  即使静态解析整条丢失，计划层窗口照样被确定性强制（见
  `tests/test_daily_directive.py::test_directive_only_window_is_enforced_by_guards`）。
- **得分**：周末/特定日合法放宽被利用（如 21:00→23:00 多 2 小时接单窗）。
- **token**：~1 次小调用/司机日 ≈ 92 次 × (约 0.8k prompt + 0.2k completion)
  ≈ 10 万 token/司机，相对 500 万上限可忽略。

### 测试
`python demo/tests/test_daily_directive.py`（11 项：合并/替换/拒绝替换语义、
窗口换算、按天缓存与重试上限、失败回退、守卫强制、周末放宽）。
原有 `test_overnight_rest_window.py`、`test_longhaul_cap_history.py` 全部保持通过。

## 3.7 相反偏好加固：去掉最后一处 D001 偏置 + 镜像规则字段

### 动机
复赛司机的偏好可能与 D001 **方向相反**（不是禁止某事，而是只做某事/必须做某事）。
审计发现三处会让这类司机吃罚分或被错误压制：

1. **长途上限是全局常量**（最严重）：`LONGHAUL_CAP=5` 来自 D001 的偏好，却被无条件
   套到所有司机——决策 system prompt 写死"每月长途软上限5单"、`_validate_llm_take_order` /
   `_pick_order` 主动压制第 6 单起的长途。专跑长途或有"长途配额"偏好的司机会被
   全季节流 → 欠单按次罚，3 个月可达 10W+。
2. **品类只有黑名单**：schema 无品类白名单，"只拉水果"这类偏好无法结构化 →
   确定性调度照接其他货，按单扣。
3. **干线距离只有上限**：无 `haul_min_km`，"低于X公里短活不接"无法结构化。

### 修复
- **长途上限改为偏好驱动**：新增解析字段 `monthly_longhaul_cap{max_orders,min_hours}`
  （+离线正则兜底可解析 D001 原文），存到 `DriverRules.longhaul_cap_orders/longhaul_min_minutes`，
  罚金走 `rule_penalties["longhaul_cap"]`。所有执行点（验单/择单/prompt 展示）改为
  **仅当该司机解析出上限时**才生效；决策 system prompt 删除写死的"5单上限"，
  并明确"没列出的限制就不存在，不要自行假设"。
- **新增 `allowed_categories` 品类白名单**："只拉/只接X"。两个方向都有代价
  （误加→全面节流；漏掉→按单罚），所以逐项语义确认（离线默认要求原文含
  只/仅/专/除了等白名单标记词）；执行端与 forbidden 同一套经济学（已知罚金→软成本，
  未知→保守硬拒）。
- **新增 `haul_min_km`**：haul_max_km 的镜像，两个评估器同点强制。

测试：`demo/tests/test_opposite_preferences.py`（10 项：无上限司机不被节流、
有上限司机软上限不变、解析/正则兜底/不臆造、白名单拒收与软成本、下限过滤）。

## 4.5 软性夜休穿越：大单优先（净收益最大化，别为 0 扣分丢大单）

### 动机（排行榜差距拆解）
某次复赛排行榜：我们净分 59587、**偏好扣分 25000(最低)**、**Token 2.18M(最低)**，
但**运营收入(净分+扣分)≈84.6k 也是最低**；第一名运营收入 ≈127k、扣分 45900。
把分差按项拆开：vs #1 运营收入 −42.6k、扣分 +20.9k，净 −21.7k = 整个差距。
**结论：差距全在毛收入，不在扣分。** 我们三项"省"指标(扣分/Token/毛收入)全垫底，
是典型的"为 0 扣分而过度保守、把值得接的大单推掉"。评分口径里夜休罚是**按天计**
(每天违规一次 2700，与违规多深无关)，所以**一笔净收益 > 当日夜休罚的大晚单是该接的**。

### 改动（`_evaluate_cargo` + 新 `_nodrive_window_covering`）
把"傍晚干线跑进夜休/禁驶窗 → 硬拒"改成**软性计价**(对齐既有长途软上限)：
- 干线若跑进**有已知罚金**的夜休窗 → 把**当日单次夜休罚** `rule_penalties["night_window"]`
  计入该单成本，`net = 价 − 里程成本 − 夜休罚`，**net>0 才接**(只有真大单能穿越)。
- **Fail-safe(关键)**：夜休窗**没有已知罚金**(解析不确定)时仍走原**硬拒**——
  这正是当年防住 −44.7 万"每晚出车"事故的那道闸，未放宽。
- **有界**：①必须在窗**开始前出发**(赴装仍受原 no-drive 拦截)；②干线必须在**同一夜窗内结束**
  (不得越过窗尾 06:00 进入次日驾驶)；③`_nodrive_window_covering` 的 `start<win_start` 保证
  **每天至多穿越一次**——穿越单做完时已进窗，调度器 D3 会让其余时间休息，扣分锁定为当天 1 次。
- 因为只在 `net>夜休罚` 时穿越，**按构造只增不减净收益**；非穿越/白天单行为完全不变。

### 测试
`python demo/tests/test_evening_bigorder_crossing.py`（12 项）：窗口判定 / 大单穿越被接 /
小单(净<罚)被拒 / 无罚金 fail-safe 硬拒 / 越过窗尾被拒 / 窗内不得起单 / 白天单不受影响 /
净值=价−里程−夜休罚；外加两项端到端 `_schedule`：确定性层会接大晚单、进窗后改为休息(不连环)。
既有 64 项测试全部保持通过。

> 验证局限：本环境 LFS 预算超额、无 `DASHSCOPE_API_KEY`，无法跑官方满月评分；逻辑用
> 桩(stub)单测 + `_schedule` 端到端校验。**上线前请按 §2 在官方平台多跑 3–5 次取均值/下限**，
> 重点看毛收入是否上抬、夜休扣分是否仍受控(只在大单日各 +1 次)。

## 6. 给接手 agent 的下一步建议

1. **任何调优都多跑几次再下结论**（§2）。
2. 想进一步抬高"下限"，可考虑：当确定性调度 `_pick_order` 已找到强净值订单时，
   不让 LLM 把它改成 wait/reposition（减少 LLM 把好货等没的坏样本）。
3. 复赛若出现新的品类/结转/区域偏好，确认**偏好解析器**能从自然语言抽出来即可，
   不要再往决策逻辑里加写死分支。
